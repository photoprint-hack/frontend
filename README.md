# Единая система управления компанией — ООО «Фотопринт»

Frontend MVP управленческой платформы: 12 KPI компании, отклонения, решения, задачи,
прогноз мощностей, качество данных и журнал действий. Подключается к Backend API на Render; встроенные frontend-моки доступны отдельным режимом.

- Стек: **React 18 + TypeScript + Vite + Tailwind CSS + React Router + Axios + TanStack Query + React Hook Form + Zod + Sonner + Lucide**.
- Тема: почти чёрный графит с ярким кобальтовым акцентом; адаптивная навигация, ясная иерархия и контрастные статусы.
- Контракт данных: API-контракт **1.2** (`snake_case`, UTC ISO-8601, `{data}` / `{items,total,page,page_size,pages}`).
- Данные: **синтетические**. Реальные персональные данные клиентов и сотрудников не используются.

## Быстрый старт

```bash
cd /d D:\photoprint
npm ci --no-audit
npm run dev
```

Открыть http://localhost:5173. По умолчанию используется Render API. Если `VITE_API_URL` явно пуст или `VITE_USE_MOCKS=true`,
задействуется mock-слой и все разделы работают без Backend.

## Что реализовано

- **Обзор компании** — 12 KPI-карточек (план / факт / прогноз / отклонение / статус),
  счётчики отклонений, решений и задач, формулы и источники каждого показателя.
- **Продажи и клиенты** — оборот, средний чек, новые/активные клиенты, повторные покупки,
  конверсия CRM, воронка по сопоставимой когорте сделок, каналы и сегменты, карточка клиента.
- **Заказы** — реестр с поиском, фильтрами, сортировкой и пагинацией; карточка заказа со
  сквозным процессом (заказ → модерация → производство → доставка → поддержка) и историей событий.
- **Производство и качество** — план/факт выпуска, очередь, lead time, загрузка мощностей,
  простои, брак и перепечатки, детализация по записям источника.
- **Финансы и персонал** — БДР и БДДС в формате план/факт, валовая маржа, обеспеченность персоналом.
- **Аналитика** — динамика KPI с планом, оборот по каналам, план/факт выпуска на данных Backend; таблица значений и сводка KPI по категориям.
- **Отклонения** — реестр критических сигналов, карточка с причиной, связанными решениями/задачами,
  переоценкой показателя и подтверждением ознакомления / устранения.
- **Решения** — реестр, форма создания (RHF + Zod + `Idempotency-Key`), карточка с полным циклом
  `new → in_progress → needs_review → completed` (+ `cancelled`), обязательным фактическим результатом,
  комментарием проверки, версией записи и историей изменений.
- **Задачи** — реестр с фильтрами «мои» / «просроченные», создание, карточка со сменой статуса,
  конфликтом версий и архивацией (только администратор).
- **Прогноз мощностей** — 4 недели, `four_week_average` в нормо-часах, дефицит/резерв/загрузка,
  явное состояние `no_data` с причиной.
- **Качество данных** — состояние 5 источников, статистика импорта, открытые проблемы,
  финансовая сверка ERP ↔ Finance, запуск проверки качества.
- **Журнал действий** — неизменяемый аудит с фильтрами и просмотром `old_values` / `new_values`.
- **Пользователи** — создание и деактивация (только администратор), матрица ролей.
- **Показатель `/metrics/:code`** — методика расчёта, динамика (график + таблица по день/неделя/месяц),
  детализация по поддерживаемым разрезам (`department`, `product`, `order`, `channel`, `cause`).
- Глобальные фильтры (период, подразделение, продукт) хранятся в URL и работают как ссылка
  «поделиться видом». Игнорируемые фильтры явно помечаются бейджем.
- Состояния: загрузка (скелетоны), пусто, ошибка с повтором, 403, 404, отсутствие сети.

## Деплой на Vercel

```bash
npm i -g vercel
vercel login
vercel --prod
```

`vercel.json` уже настроен: сборка `npm run build`, статика из `dist/`, SPA-rewrites на
`index.html` (чтобы прямые заходы на `/orders/:id` работали) и security-заголовки.
Для боевого контура задайте переменные окружения в проекте Vercel (см. ниже).

## Переменные окружения

Копируем `.env.example` → `.env.local`:

| Переменная | Значение по умолчанию | Описание |
| --- | --- | --- |
| `VITE_API_URL` | `https://backend-v8pa.onrender.com/api/v1` | Полный базовый адрес Backend, **включая префикс `/api/v1`**. Явное пустое значение = моки. |
| `VITE_USE_MOCKS` | `false` | Принудительно включить моки даже при заданном `VITE_API_URL`. При пустом URL моки включаются автоматически. |
| `VITE_MOCK_LATENCY` | `260` | Задержка mock-ответов в мс (демо состояний загрузки). |

Подробнее о переключении на реальный Backend — в [BACKEND_INTEGRATION.md](./BACKEND_INTEGRATION.md).
Ход работ и решения по коду — в [AGENT_LOG.md](./AGENT_LOG.md).

## Безопасность

- Access Token хранится **только в памяти** (`lib/auth/token-store.ts`), не в `localStorage`.
- Refresh Token — httpOnly-cookie от Backend (`withCredentials: true`), фронт его не читает.
- При 401 запрос повторяется один раз после обновляния токена; параллельные 401 используют
  одну очередь refresh. При неудаче пользователь разлогинивается и уходит на `/login`.
- 403 не разлогинивает: показывается состояние «недостаточно прав».
- Права (RBAC) на фронте нужны только для UI; фактические ограничения обеспечивает Backend.
